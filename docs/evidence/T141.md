# T141 — Fork startup initialization

- Outcome: **measured startup improvement; performance qualification remains unproven**.
- Baseline: Xi `9f0b8d8`, fork `f299f16`, plus the existing application worktree.
  The application was identical in before/after builds; this is not clean-HEAD evidence.
- Candidate: runtime-specific text helpers, lazy timing segmentation and lazy Bun
  Markdown initialization. Native binaries, input/frame scheduling, editor and services
  are unchanged. Fork revision: `ef3901c` (`xi-lazy-ffi`); final validation is recorded below.
- Host: shared Linux 6.8.0 arm64, Bun 1.3.13, Node 26.4.0 for portable tests,
  Core/React/Solid 0.5.11, React 19.2.0, Solid 1.9.12, Python 3.13.15,
  pyte 0.8.2 / wcwidth 0.8.4. Specifications 01/05/12/15; no budget changes.

## Observable result

Bun uses its native width/ANSI helpers without evaluating Node's fallback packages.
Node retains its existing fallback implementation. Importing the unused timing widget
no longer creates an ICU segmenter. Markdown's parser initializes synchronously on
first use on Bun; Node keeps its static import. No placeholder or fake ready signal
was introduced. Markdown's first use still pays initialization cost.

The source package uses existing runtime conditions. The published-package patch wraps
its already-bundled Markdown parser in a cached initializer, preserving executable
packaging. Source tests cover parser reuse, Unicode and Markdown; the compiled consumer
smoke checks actual initial and incremental Markdown frames with a controlled highlighter.
This does not qualify real grammar-loading latency.

## Discarded attempts and harness repairs

- Conditional dynamic fallback imports avoided eager ICU construction but retained
  unused code and did not establish a reliable compiled startup win (`startup-40/`).
- Ordinary `bun install --force` reused stale patched JavaScript. `final-startup-40/`
  therefore did not measure its intended runtime-helper candidate. A fresh isolated
  `BUN_INSTALL_CACHE_DIR` and installed-JS hashes corrected the experiment.
- Native binding batching did not establish a gain: paired medians Core −0.87 ms,
  React −0.19 ms, Solid −1.21 ms; all bootstrap intervals crossed zero
  (`batch-startup-40/`). That extra machinery was removed.
- An initial generated Markdown helper used `require` in a pre-transpiled `// @bun`
  package, where it was unavailable. An alias hid the parser from bundling. The final
  patch retains the bundled parser inside a cached initializer instead. The earlier
  `markdown-startup-40/` measured a broken optional Markdown path and is rejected.
- The smoke fixture initially lacked the required style, failed to wait for highlighting,
  and one CLI compilation omitted `--format esm`. Corrected checks use a real style,
  controlled asynchronous highlighter, fail-fast compilation and production ESM flags.
  These failed checks are not performance evidence.
- CPU profiles and binding traces were diagnostic, instrumented runs, not ordinary
  startup measurements (`profile/`, `binding-trace/`).

## Qualification limits

This is a shared-runner diagnostic. Physical key-to-visible latency, paired pinned
Neovim, CPU/total allocation/retained heap/native-worker attribution, the complete
large-file and service-load matrix, non-Linux platforms and a full declarative UI
migration are unproven. No claim of zero allocation or native-level qualification.
Existing first-key failures remain open. Optional Markdown first-use latency is not
qualified by the mock-highlighter smoke. No visual/layout changes or snapshot approvals.
