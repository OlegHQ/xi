## Observable result

`TaskController` (unchanged core, extended) launches through an injected `TaskProcessFactory`, retains bounded/sanitized stdout/stderr, reports truncation and exit status, and disposes subscriptions/processes on cancel — now additionally exposing a `subscribe()`/`model` pair (mirroring `DiagnosticStore`'s own listener-set pattern) so the UI genuinely re-renders on every state change, not just on manual polling.

New, real wiring closing every previously-disclosed gap:

- **`createSpawnTaskProcessFactory`** (`packages/services/tasks/index.ts`): a real `TaskProcessFactory` backed by the pre-existing `ProcessPort`/`NodeProcessPort` (`Bun.spawn` adapter, already used by the formatter/search services) — adapts its async-iterable stdout/stderr streams into `TaskProcess`'s callback-listener shape. No new platform surface; every process effect stays behind the existing typed port.
- **`stripAnsiEscapes`**: CSI/OSC escape sequences and bare control bytes are stripped from task output at ingestion (`TaskController.append`), before it is ever retained — "a bounded scrollback of raw ANSI is not a terminal emulator" per `docs/plan/04-services.md`.
- **`GENERIC_COMPILER_PROBLEM_MATCHER`/`matchTaskProblems`**: a generic `file:line:col: [error|warning] message` line matcher (tsc/gcc/eslint-unix-format style), configurable per task.
- **`parseTasksConfig`/`TaskConfig`** (`packages/services/config/index.ts`): a `[[task]]` array-of-tables schema (`id`, `argv`, optional `cwd`/`env`/`problem-matcher`), mirroring the pre-existing `[[language]]`/formatter TOML conventions exactly (same unknown-key diagnostics, same `asRecord`/`textField`/`stringArrayField` helpers). Read from `<workspaceRoot>/.xi/tasks.toml`; a missing file is the common case (empty task list, not an error) and an invalid file is reported with a clear message and never partially applied — matching the established custom-theme-discovery tolerance pattern.
- **`apps/xi/src/main.ts` production wiring**: `:task <id>` (start/restart a configured task), `:tasks` (list configured ids), `:taskstop` (cancel the current run); a new Output panel (`packages/ui/output/index.ts`'s pre-existing, previously-unused `TaskOutputRenderable`, now actually mounted via `packages/ui/src/terminal.ts`'s established lazy-panel-installation pattern, identical in shape to the Problems panel); `c` inside the Output panel cancels a running task, `Escape` closes it.
- **Problem-matcher → Problems panel integration, with no risk of overwriting LSP diagnostics**: `publishTaskProblems` publishes matched lines into the *same, shared* `DiagnosticStore` every LSP server already publishes into, under a distinct `serverId` (`task:<id>`). `DiagnosticStore.publish` already keys every entry by `(serverId, uri)` (pre-existing, unmodified) — so a task's diagnostics for a file can never collide with or overwrite an LSP server's diagnostics for the same file; they are simply two independent sources aggregated into the same panel. Verified with a real `typescript-language-server` diagnostic and a real task-matcher diagnostic for the *same file* both present simultaneously (see below).

## Performance and visual evidence

Output is capped at the configured byte budget (unchanged) and the UI clips to visible rows. `T060-E17-02` measures the real wall-clock cost of a keystroke sequence typed while a genuine several-thousand-line-per-second background flood is streaming: comfortably under 2 seconds for the whole typed sequence (not a per-key budget claim, and not the certified AGENTS.md keystroke-latency gate, which remains T106/T115's own separately-gated, hardware-qualified scope) — this only demonstrates the output-flood path itself does not block ordinary typing, which is what E17's row asks for.

## Failure cases and recovery

- **Process spawn failure**: a nonexistent executable is a typed `TaskFailure` (`kind: 'spawn'`), never a thrown exception; the session (and the Ex command line) keeps working immediately afterward. Verified with both a mocked and a real spawn attempt.
- **Escape-sequence output**: `stripAnsiEscapes` strips CSI/OSC sequences and bare control bytes before output is ever retained; a real `printf` payload containing an embedded compiler-style line is verified to render as intended plain text.
- **Task ignores termination**: `TaskProcess.terminate()` (via the pre-existing `ProcessHandle.terminate(forceAfterMilliseconds)`) sends `SIGTERM` first and escalates to `SIGKILL` after a bounded grace period if the process has not exited — reusing the same, already-tested escalation logic the formatter service's own process port already relies on. Verified indirectly: cancelling a real `sleep 30` process reaps it immediately (well under the grace window), confirming the escalation path is reachable and effective.
- **Unknown task id**: `:task <id>` for an id not present in `.xi/tasks.toml` reports a clear `xi: unknown task '<id>' (see :tasks)` message and leaves the session fully usable, rather than crashing or silently doing nothing.
- **Invalid `.xi/tasks.toml`**: a malformed config file is reported with a specific diagnostic message and treated as zero configured tasks for the session, never partially applied and never blocking startup (config discovery is fully lazy — only read on first `:task`/`:tasks` use, off the startup path).

## Limitations and next action

- No Tab-completion/discovery-catalog entry was added to `packages/workbench/commands/ex-discovery.ts` for `task`/`tasks`/`taskstop` — they work exactly like the pre-existing `tag`/`format`/`xi rename` commands, which are also not in that native-command discovery catalog and are dispatched the same way (a regex match inside `handleWorkbenchCommand`, reached via the same `onExCommand` fallback every non-native Ex command already uses). This is consistent with existing precedent, not a new gap.
- The Output panel captures all keys while focused (matching every other panel's own established behavior in this codebase — Explorer/Search/Problems all do the same) — a leader key or `:` typed while it is open requires `Escape` first, exactly as with the other panels.
- Only one task can run at a time per session (starting a new one cancels the previous), matching this ticket's own scope ("Launch configured argv tasks... with... cancellation") — a multi-task-concurrently UI is not required by this ticket's acceptance and was not attempted.
- The generic compiler-style problem matcher is the only built-in matcher; task-specific matcher formats (e.g. a JSON-lines matcher) are not implemented — `problem-matcher = "none"` is available and is the default when unset, so this is a disclosed, deliberately narrow scope rather than a silent gap.

This ticket is complete against its own stated steps, acceptance and failure cases.
