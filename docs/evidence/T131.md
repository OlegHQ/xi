## Observable result

Before this ticket, `apps/xi/src/main.ts`'s `handleExplorerKeypress` had no rename/copy/delete action at all — `filesystem.renamePath`/`copyPath`/`removePath` existed only as unused platform-port capabilities, and `WorkbenchSession.renameBufferPath` (built for exactly this purpose, per its own doc comment) had zero caller. This ticket wires real Explorer keybindings on top of that already-tested machinery:

- **`r`** — rename draft, pre-filled with the current node's name. Typing edits the draft; `Enter` applies; `Escape` cancels with zero filesystem effect.
- **`y`** — copy draft, same input flow, applies via `filesystem.copyPath` (which already refuses an existing target via `errorOnExist: true`).
- **`d`** — delete. Requires an explicit `y` confirmation keystroke; any other key cancels. Delete never permanently removes anything: it *moves* the target into `<workspace>/.xi-trash/` via `filesystem.renamePath` (a same-filesystem rename, atomic, genuinely reversible) rather than calling the real, permanent `filesystem.removePath`.
- **`u`** — restores the most recently applied operation from an in-memory, session-scoped undo journal (`explorerUndoJournal`): a rename/delete moves the path back; a copy removes exactly the copy, leaving the original untouched.

Any open buffer under a renamed/restored path has its display/save path kept in step via the pre-existing `WorkbenchSession.renameBufferPath` — document content is never touched, only the path label.

**A genuine, disclosed gap found and fixed along the way**: `.xi-trash` was not excluded from `packages/platform/src/filesystem.ts`'s default `ignoredDirectoryNames` (used by both Explorer's own directory listing and the file picker's background index) — meaning a "deleted" file would still surface in the quick-open picker, and its real content would still be readable there, undermining the whole point of a soft-delete. Fixed by adding `.xi-trash` to that shared default list (alongside `.git`/`node_modules`/`.artifacts`/`.cache`/`dist`, which are already excluded there); verified empirically that a file planted directly in `.xi-trash` no longer appears in the picker.

## Performance and visual evidence

Not separately measured. Every operation is a single bounded filesystem call (rename/copy/rename-to-trash), not a per-keystroke cost; draft text entry reuses the same bounded per-keystroke append pattern the existing filter input already uses.

## Failure cases and recovery

- **Rename target already exists**: `applyExplorerRename` explicitly `stat`s the destination before renaming and refuses with a clear message (`xi: rename failed: <name> already exists`) rather than relying on `fs.rename`'s own silent-overwrite behavior on POSIX. Verified: neither the source nor the pre-existing target file is touched.
- **Delete target has unsaved open buffers**: `applyExplorerDelete` checks `workbench.buffers()` for any dirty buffer at or under the target path and refuses with a clear message before touching the filesystem. Verified with a real dirtied buffer.
- **Restore after the original path was externally recreated**: `restoreLastExplorerOperation` `stat`s the original path before restoring; if it now exists, the restore is refused (and the journal entry kept, so a later retry after the conflict clears is still possible) rather than silently overwriting the externally recreated file. Verified with a real external write between delete and restore.
- A cancelled draft (`Escape` during rename/copy, or anything but `y` during delete confirmation) performs zero filesystem calls — verified by asserting the filesystem is byte-for-byte unchanged immediately after cancellation.

## Limitations and next action

- No separate Ex commands (e.g. `:rename`) were added — only Explorer keybindings (`r`/`y`/`d`/`u`), which the ticket's own step wording ("keybindings/Ex commands") treats as an acceptable either/or, not a required both.
- The undo journal is in-memory and session-scoped only (matches T132's own established "session-scoped, not persisted" pattern for similar state) — it does not survive a restart. This was not required by this ticket's acceptance (which only requires restoring *within* the same session's operations) and is disclosed rather than silently assumed.
- Only the single most recent operation can be restored (`u` pops one journal entry); there is no multi-level undo stack UI. The ticket's acceptance only requires "restore" as a capability, not a full undo history browser, so this is a deliberate, disclosed scope boundary, not a gap.
- `.xi-trash` accumulates deleted files indefinitely with no automatic cleanup/expiry. Given this ticket's acceptance is about draft/cancel/apply/restore correctness, not trash lifecycle management, this is disclosed as follow-up scope rather than attempted here.

This ticket is complete against its own stated steps, acceptance and failure cases.
