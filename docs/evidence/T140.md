# T140 — Compiled Solid versus React and Core

- Outcome: **bounded comparison completed**; full UI adoption and performance qualification remain **unproven**.
- Base revision: `bca7392`, with the existing application worktree changes. The three
  executables were built from the same tree; this is not a measurement of clean HEAD.
- Environment: shared Linux arm64 host, Bun 1.3.13, TypeScript 7.0.2, OpenTUI
  Core/React/Solid 0.5.11, React 19.2.0, Solid 1.9.12; pyte 0.8.2 / wcwidth 0.8.4.
- Scope: T140's bounded adapter comparison, specs 01/05/12/15/16. No budget changes.

## Observable behavior and comparison controls

`spikes/ui-solid/launch.tsx` replaces exactly the real status-message surface replaced
by the React candidate. Both mount a stable box/text pair before the usable editor
frame, subscribe to existing status and command-line read ports, and use the same
renderer, input router, document, Vim engine, services and editor paint implementation.
The imperative status surface is disabled only because its declarative replacement
owns that presentation. There is no second text store or input/frame scheduler.

`spikes/ui-solid/build-cli.ts` builds all three candidates with bytecode, minification,
production React definitions and disabled development tooling. All Core imports resolve
to the same root patched package. The official Solid transform runs at build time and
replaces server entrypoints with its reactive client runtime. The application imports
the renderer, not the JSX compiler/preload plugin. A reactive update/disposal regression
also rejects an inert server-runtime implementation.

The first Solid attempt used a conditional root. On clearing status, the pinned host's
root cleanup removed the imperative editor siblings too. The failed PTY run remains in
`.artifacts/ui-solid/smoke/`. Both adapters now keep their own surface mounted and toggle
visibility. The corrected full smoke passed all four React/Solid idle/task journeys.
The focused compiled test verifies real status publication, clearing without destroying
editor siblings, and disposal of the real adapter subscription on renderer destruction.
This is a temporary integration arrangement: a full migration should give one framework
root ownership of composition and expose the retained editor as a custom component.

## Startup result

60 fresh processes per variant, filesystem warm, randomized condition order within
each session (seed 135), PTY 120×40, 400 normal ASCII lines. Completion requires parsed
usable editor cells/cursor, not a readiness marker. Startup includes VT parsing cost;
each process immediately verifies the first `j` motion, exits cleanly and checks the
unchanged source bytes. The independent injector is prepared before application startup.
Percentiles use nearest rank; p99 equals max with 60 observations.

| Variant | Startup p50 / p95 / p99 / max (ms) | Median early RSS (MiB) | Executable (MiB) |
| --- | --- | --- | --- |
| Core | 78.29 / 91.62 / 115.25 / 115.25 | 128.27 | 133.56 |
| React | 90.88 / 100.15 / 112.75 / 112.75 | 137.21 | 136.75 |
| Solid | 88.35 / 95.85 / 113.55 / 113.55 | 133.01 | 135.94 |

Solid lowers median startup by **2.53 ms (2.8%)** versus React here, but remains
**10.06 ms above Core**. Pairing by session gives median deltas React−Core +13.05 ms,
Solid−Core +9.88 ms, Solid−React −2.47 ms. A 10,000-resample paired median bootstrap
(seed 140) gives diagnostic 95% intervals of +10.95…+14.10, +8.94…+11.33 and
−4.13…−1.26 ms respectively. These intervals do not remove shared-host uncertainty.
Early RSS is 4.20 MiB lower with Solid than React, and the executable is 0.81 MiB smaller.
RSS is a snapshot after the first-key probe, not retained heap/native allocation proof.

This is a fresh matched comparison, not subtraction against T136's older React build:
the React status candidate now mounts the same stable hidden nodes as Solid. The old
roughly 9.5 ms React overhead is not a constant library tax. Neither result isolates
module initialization, catalogue imports, native initialization and first layout costs.

## Full idle/task journey result

**72/72 journeys passed; 8,712 verified key completions.** Each variant/load condition
has 12 fresh processes and 1,452 events: 12 first keys, 240 paced motions, 360 held
Down arrows, 360 burst motions, 240 paced Unicode insertions and 240 burst insertions.
Every journey checks the real status error, command-line takeover, task liveness when
loaded, clean exit and exact final file bytes. First-key samples precede task launch;
likewise startup in the task condition happens before task load begins.

Paced motion uses 50 ms intervals, held arrows 60 Hz, burst motion 1 ms intervals;
insertion mixes ASCII/é/漢 with 20 paced and 20 burst characters. The task emits 2 KiB
about every 3 ms; its output panel is closed before measuring editor keys, while the
real process and output handling continue. This is not the full service-load matrix.

## Limitations and decision

Solid is a credible declarative candidate with a modest measured startup/memory advantage
here. Switching frameworks alone does not meet the user's goal of eliminating startup
cost, and this one-surface comparison cannot predict whole-shell cost. Keep the custom
editor viewport separate whichever framework owns shell/panels. Any next migration must
show that it removes imperative composition and passes matching functional/latency gates.

No physical pixels, qualified reference host, full service/action/large-file matrix,
CPU/GC/allocation rates, native/worker peaks, or complete migrated UI were measured.
This run does not repeat the pinned Neovim comparison from T136 and therefore cannot
certify the ≤3 ms Neovim overhead requirement. First-key failures remain visible;
no scheduler/input contract or budget is relaxed. Full UI visual parity is not claimed.
