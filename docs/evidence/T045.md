## 2026-09-17 (later): E13 crash recovery wired into the production CLI for the first time

**E13** ("Crash after edit/save/directory-step then restart" → "Bounded recovery loss, external disk changes preserved, journal actionable") had zero coverage, and — unlike E04 — turned out to be a genuinely wireable gap rather than a missing feature: `packages/services/persistence/index.ts`'s `PersistenceService.checkpoint`/`recover`/`clearRecovery` (T037's own module; unit/fixture-tested in `tests/persistence/t037.test.ts`, already `done`) was never called from `apps/xi/src/main.ts` at all. Crash recovery existed only in the untested-in-production service layer.

**Wiring added** (`apps/xi/src/main.ts`):
- A debounced, best-effort checkpoint write (`scheduleCheckpoint`/`writeCheckpoint`, 1.5s after the last commit to a dirty document) hooked into the existing `WorkbenchSession.onDocumentChange` callback — off the keystroke path, matching AGENTS.md's "no synchronous process/filesystem calls... in a keystroke path" rule; a burst of rapid edits reschedules the same timer rather than writing on every commit.
- `openDocument` now calls `persistence.recover(path, documentId, ...)` after a successful `openFile`. If the checkpoint's own recorded disk baseline still matches the current disk identity (`kind: 'recovered'`), the recovered document (already reconstructed by `recover()` itself) replaces the freshly-opened one and a message/marker reports it. If the disk changed since the checkpoint (`kind: 'disk-diverged'`), recovery is refused and the *current disk content* opens instead — an external change is never silently overwritten by older recovered content.
- `saveDocument` calls `persistence.clearRecovery(path, ...)` after every successful save, so a clean save leaves no stale journal for a later, unrelated crash to "recover" from.

**Verified with three real production PTY scenarios** (`tests/e2e/t045-e13-crash-recovery-pty.py`, 3/3 clean runs), each using an actual `SIGKILL` to simulate a crash (not a mocked failure):
1. Edit, real `SIGKILL` (no save, no clean quit), reopen: disk is confirmed untouched by the crash itself, the reopen fires a real `recovered` marker, and saving afterward produces exactly the pre-crash edit's content.
2. Same, but the file is changed on disk *before* reopening: a `disk-diverged` marker fires instead, and the external change is confirmed never overwritten.
3. Edit, clean `:wq`, reopen: no recovery marker fires at all — the clean save's `clearRecovery` call left nothing to recover.

**Executed validation**: `bun x tsc --noEmit`/`bun run check` pass; `tests/e2e/t045-e13-crash-recovery-pty.py` added to `tools/verify-suite.ts`'s `interaction` selector, `bun run test:e2e -- --suite interaction` passes all 43 fixtures; every other `tests/e2e/*.py` fixture not in that selector re-checked individually and still passes (this change touches the shared `openDocument`/`saveDocument` paths every file-backed test exercises); `test:ui` 7/7, `test:unit` 32/32, `test:services` 28/28, `python3 tools/plan.py check` (130 tickets).

**Limitations**: the "directory-step" half of E13's own row (crash during a directory rename/copy/delete operation) is moot given E04's finding that no such Explorer feature exists yet to crash during. Recovery only reconstructs plain text content (`RecoveryCheckpoint.normalizedText`/line-ending metadata) — selection/cursor position and split/session layout are not part of this checkpoint (that is T095's own, separately-scoped session-persistence mechanism). The checkpoint debounce (1.5s) is a fixed constant, not configurable, and was not itself performance-budgeted against `docs/plan/12-performance.md` (T106/T115's scope, not this ticket's).

## 2026-09-17 (later still): E12 bracketed paste wired into the production CLI for the first time

**E12** ("Legacy/enhanced keys, bracketed paste, required supported mouse protocols" → "One event delivery, no pasted commands, no Ctrl-C accidental exit") had zero coverage. Investigation found the "no pasted commands" half was accidentally already true (nothing consumed OpenTUI's `paste` event at all, so paste had zero effect), but that also meant paste was completely non-functional — a real gap, not a satisfied requirement.

**Confirmed before wiring anything**:
- OpenTUI's renderer already auto-enables bracketed-paste mode (`\x1b[?2004h`) at Xi startup and correctly delivers a full bracketed-paste sequence as one opaque `paste` event (`renderer.keyInput.on('paste', (event: PasteEvent) => ...)`, `event.bytes: Uint8Array`) rather than as individual keypresses — verified with a real PTY probe (a pasted `:wq!\r` produced zero effect before this pass, confirming it was never parsed as keystrokes).
- The Vim engine already fully modeled paste as an opaque, never-reparsed input end to end: `packages/vim/parser/index.ts`'s `case 'paste'` (explicit comment: paste bytes "remain one paste intent and are never recursively parsed"), and both `planVimInsertInput`/`planVimMultiInsertInput` already accept a `{kind:'paste', bytes}` input variant (UTF-8 decode, `\r\n?` → `\n` normalization). Only `packages/workbench/vim-session/index.ts`'s `executeCommand` had zero branch for it (confirmed via `grep -n "'paste'"`, zero matches) — the session layer, not the engine, was the actual gap.

**Wiring added**:
- `packages/ui/src/terminal.ts`: new `onPaste?: (bytes: Uint8Array) => void` option on `OpenTuiWorkbenchOptions`, subscribed via `renderer.keyInput.on('paste', (event: PasteEvent) => { options.onPaste?.(event.bytes); flushFrame(); })`.
- `apps/xi/src/main.ts`: `onPaste` routes to `activeSession()?.handlePaste(bytes)`, guarded to skip when any overlay/panel (Explorer, Search, Problems, Outline, Picker, leader-pending) or the command line is focused — pasting into those surfaces is a disclosed, un-wired limitation, not silently miswired into the editor buffer. Emits an `XI_PASTE` test marker with the byte length.
- `packages/workbench/vim-session/index.ts`: new public `handlePaste(bytes: Uint8Array): boolean` on `OwnedVimSession`. Only Insert/Replace/Virtual-replace mode consumes it (mirrors the existing `command.kind === 'insert-key'` branch's exact `planVimMultiInsertInput`/null-session/`makeInsertSelections`/`makeNormalSelection` handling); a Normal-mode paste is a safe no-op message rather than silently doing nothing unexplained. Sets `insertTainted = true` so an in-progress dot-repeat insert recording (T024/T130) is correctly disqualified — pasted text is one atomic insertion, not a literal single-key stream matching T024's insert-repeat replay model.

**Verified with a new real production PTY test** (`tests/e2e/t045-e12-bracketed-paste-pty.py`, 3/3 clean runs): sends a real bracketed-paste sequence (`\x1b[200~...\x1b[201~`) whose payload contains an embedded `:wq!\r` and a raw Ctrl-C byte (`\x03`), both in Normal mode (must be a safe no-op, no crash, no buffer change) and after entering Insert mode (must insert the bytes literally as text, must not execute `:wq!`, must not exit on the embedded Ctrl-C). Confirms via exact on-disk bytes after `:wq` that the pasted content landed as literal text with `\r`→`\n` normalization and nothing else.

**Executed validation**: `bun run check` (toolchain/types/public-boundary/lint) passes; `tests/e2e/t045-e12-bracketed-paste-pty.py` added to `tools/verify-suite.ts`'s `interaction` selector, `bun run test:e2e -- --suite interaction` passes all 45 fixtures (one transient Xvfb display-collision on `t128-e22-splitter-xterm-pty.py` during an earlier run of the full suite, confirmed transient by rerunning that fixture standalone — the same pre-existing environment flake documented earlier in this file, not a regression); `test:unit` 32/32, `test:services` 28/28, `test:ui` 7/7; `python3 tools/plan.py check` (130 tickets); `tests/e2e/t051-completion-pty.py`, `t055-formatting-pty.py`, `t071-native-navigation-pty.py`, `t088-language-edits-pty.py`, `t088-primary-only-pty.py` (the fixtures switched to explicit `:q!` for the T038 quit-safety fix) re-checked individually and still pass.

## 2026-09-17 (later still): E02 given real production PTY coverage; two genuine pre-existing bugs found and fixed in the picker-preview path

**E02** ("File picker preview/cancel/pin, switch split, return" → "Source view restored, no dirty preview discarded, same buffer text in two views") had zero coverage. Investigating it surfaced two genuine, previously undiscovered bugs in `apps/xi/src/main.ts`'s picker-preview wiring — workbench-owned code, legitimate maintenance per AGENTS.md since this ticket's own dependency, T038, owns `packages/workbench/`:

1. **Data loss.** `previewViewId` was a single stale pointer never cleared when the previewed buffer got promoted (dirtied) or explicitly committed. Escape then unconditionally force-discarded whatever it still pointed to via `workbench.closeView(id, 'discard')` — which supplies an explicit `decision` argument, bypassing the dirty-buffer guard entirely — silently destroying real, already-promoted/pinned edits that merely happened to still share the stale pointer. Empirically confirmed with a throwaway debug probe before the fix: preview a file, commit it, edit it (auto-promoting it to pinned/dirty per the existing "first edit also promotes it" `onStateChange` hook), preview a different, brand-new file, and press Escape — the pinned, dirty buffer got discarded (`XI_PICKER_DISCARD_PROBE {"dirty":true,"preview":false,"pinned":true}` right before the destructive `closeView` call).
2. **Duplicate documents.** The picker's file-index entries always use absolute paths, but a relative CLI argument (e.g. `xi alpha.txt`) was stored as-is on the initial buffer, so navigating the picker back onto that same already-open file failed the naive `buffer.path === path` string comparison and opened a second, independent document for the identical file. Empirically confirmed: buffer count grew from 2 to 3 when re-navigating to a file that was already open.

**Fixed** by: resolving the CLI file argument to an absolute-looking path in `resolveFileArgument` (`apps/xi/src/main.ts`) so it is comparable via the same `filesystem.workspaceRelativePath` normalization every other subsystem already uses (Explorer/search/LSP) — done without a `node:path` import, since architecture forbids that outside `packages/platform`; a new `discardStalePreview` helper that only ever closes a view whose buffer is still actually `preview === true` (never a promoted/committed one); and clearing `previewViewId` at every point a preview buffer stops being a preview (promote-on-edit, explicit commit, or a new preview superseding it).

**New production PTY test** (`tests/e2e/t045-e02-picker-preview-pty.py`, 3/3 clean runs): preview and commit a file, edit it (promoting it), preview an unrelated brand-new third file and cancel that preview, confirms the edited buffer was never discarded, then navigates the picker straight back onto the edited file by name and confirms it reuses the same buffer (no duplicate document, no new preview marker) with the edit still present, verified on disk via `:w`.

**Two existing tests had to be adjusted** for the now-corrected, more eager preview lifecycle (a superseded, never-edited preview is now discarded as soon as a newer navigation supersedes it, rather than lazily deferred to Escape — and navigating back onto an already-open file no longer opens a spurious duplicate preview): `tests/e2e/t039-picker-pty.py` and `tests/e2e/t128-named-terminal-pty.py` both previously queried a string ("README") whose fuzzy top-match happened, by the time the query finished, to fuzzy-re-match the *already-open* file itself — under the fixed dedup behavior this correctly stops emitting a new preview/cancel marker, since nothing is left over to discard. Both were changed to query a genuinely different, unopened file instead (`t128`'s tmux workspace only had one file, so a second `other.txt` fixture file was added). This is a real behavior improvement being reflected in the tests, not a weakened test.

**Executed validation**: `bun run check` (toolchain/types/public-boundary/lint) passes; `t045-e02-picker-preview-pty.py` added to `tools/verify-suite.ts`'s `interaction` selector, `bun run test:e2e -- --suite interaction` passes all 46 fixtures; `test:unit` 32/32, `test:services` 28/28, `test:ui` 7/7; `python3 tools/plan.py check` (130 tickets); the two adjusted tests (`t039-picker-pty.py`, `t128-named-terminal-pty.py`) and the closely related `t127-panel-pointer-picker-pty.py`, `t064-compiled-pty.py`, `t064-ex-pty.py` re-checked individually and pass.

**Limitations**: the "pin" verb in E02's own row (an explicit user-facing pin action distinct from "first edit auto-promotes") remains unimplemented — `WorkbenchSession.pinBuffer`/`promoteBuffer` exist as service capabilities but are never exposed through any keybinding or Ex command; only the auto-promote-on-edit path is wired. Separately, this investigation also found `:wa`/`:qa` (write-all/quit-all across every open buffer) are declared as discoverable native Ex commands in `packages/workbench/commands/ex-discovery.ts` but have **no execution wiring at all** in `apps/xi/src/main.ts`'s `handleWorkbenchCommand` (which only handles `split`/`vsplit`/`q`/`q!`) — `:wa`/`:qa` silently fall through to the per-view Vim Ex parser instead of operating workspace-wide, a distinct, disclosed gap for whoever picks up multi-buffer Ex commands next. "Switch split, return" (E02's own row) was not independently exercised as a picker-specific scenario in this pass (split/return itself is covered elsewhere, e.g. T038's evidence).

## 2026-09-17 (later still): E03 given real production PTY coverage; a genuine reveal-on-open race condition found and fixed

**E03** ("Tree expand/filter/reveal and watcher insertion" → "Stable selected path, no unsolicited focus/scroll") already had real-watcher-event coverage through the launched Explorer panel via `tests/e2e/t040-explorer-pty.py` (insertion/rename preserve selection identity) — the 2026-09-15 completion audit's note that E03 was "not demonstrated through the launched Explorer panel" was already stale by the time this addendum was written. What remained genuinely uncovered: reveal-on-open (auto-selecting the already-open file when Explorer first opens), filter narrowing/restoring through the real CLI (only component-level in `t040-explorer.test.ts`), and "no unsolicited focus" specifically while the Explorer is *closed* and a watcher event fires in the background.

Investigating reveal-on-open surfaced a genuine, previously undiscovered race condition in `apps/xi/src/main.ts`'s `openExplorer`: it fired `explorerTree.expand(root, false, ...)` and `explorerTree.reveal('workspace', activeRelativePath, ...)` **concurrently** (both `void`-called back to back). `ExplorerTree.expand()` synchronously sets `node.expanded = true` and `node.loadState = 'loading'` *before its first await point* (`packages/services/files/index.ts`). `reveal()`'s own "does this node need expanding" check (`!parent.expanded || parent.loadState === 'unloaded' || ...`) can therefore see the concurrent expand's in-flight state and conclude the root is "already expanded" — then immediately search `parent.children` for the next path segment before that concurrent expand's own `enumerateDirectory` call has resolved and actually populated them. Empirically confirmed with a throwaway debug probe: opening Explorer on a file nested one directory deep produced `reveal` → `{"ok":false,"error":{"kind":"invalid-path","message":"path component is not present: src"}}` every time, and the Explorer silently stayed on the root selection instead of ever revealing the active file.

**Fixed** by sequencing them: `openExplorer` now awaits the root's own `expand()` before calling `reveal()`, so `reveal()` only ever walks a root whose children are genuinely populated (and, since the root is now already `loadState: 'ready'`, `reveal()`'s own re-expand guard correctly no-ops for it rather than racing a second concurrent load).

**New production PTY test** (`tests/e2e/t045-e03-explorer-filter-reveal-pty.py`, 3/3 clean runs): opens a file nested inside a subdirectory and confirms Explorer auto-reveals and selects it (parent directory expanded) with zero manual navigation; types a filter query and confirms the visible row count narrows, then confirms clearing it restores the full count; closes the Explorer and confirms a real filesystem insertion afterward never re-opens/re-triggers the Explorer's refresh marker and never steals keyboard focus from the editor (typed keystrokes land in the document, confirmed on disk).

**Executed validation**: `bun run check` passes; new fixture added to `tools/verify-suite.ts`'s `interaction` selector, `bun run test:e2e -- --suite interaction` passes all 48 fixtures (one transient Xvfb display collision on `t128-e21-textdrag-xterm-pty.py` during the full run, confirmed transient by rerunning standalone — a pre-existing environment flake documented earlier in this file, not a regression); `tests/e2e/t040-explorer-pty.py` re-checked individually and still passes (this change touches the shared `openExplorer` path it also exercises); `test:unit` 32/32, `test:services` 28/28, `test:ui` 7/7; `python3 tools/plan.py check` (130 tickets).

**Limitations**: "no unsolicited scroll" (the other half of E03's acceptance) was only indirectly exercised — scroll-position preservation specifically during a watcher-triggered insertion *while Explorer is open and scrolled* was not independently verified (T129's own panel-scroll evidence covers scrollbar mechanics generally, not this specific interaction). E06/E16, screenshot review, and typing-load profiling remain unaddressed.

## 2026-09-17 (later still): explicit keyboard-only journey coverage, and a real dot-repeat defect found and fixed along the way

T045's own acceptance requires "Keyboard journeys require no mouse." Before this pass that had strong *implicit* evidence (every fixture this session's T045 work added is itself keyboard-driven) but no single, explicit, dedicated demonstration that a realistic end-to-end session — navigate, edit, dot-repeat, search, Explorer rename (T131), theme switch (T132), save+quit — never requires a mouse. Checked first via `grep -rln "require no mouse\|keyboard-only\|no mouse required" docs/evidence/*.md`, which found only `docs/evidence/T063.md` disclosing this exact gap as unproven for its own scope.

New: `tests/e2e/t045-keyboard-only-journey-pty.py` (3/3 clean runs) chains one representative, zero-mouse action from every major subsystem this session touched, through the real production CLI, asserting no byte of the script is a mouse escape sequence.

**Building this test surfaced a real, previously-undetected defect**, not a test-methodology issue: the first run failed with the dot-repeat step (`gg$.` replaying an `A<text><Esc>` insert onto a different line) producing no change at all. Isolating it (progressively simpler PTY probes, removing navigation, removing `gg`, removing all navigation) showed dot-repeat failed for **any** inserted text containing a literal space character, regardless of navigation — not a `gg`-specific or navigation-timing issue as first suspected. Root cause, found by adding temporary `XI_DOT_DEBUG`-gated `console.error` tracing (removed once diagnosed) to `packages/workbench/vim-session/index.ts`'s `executeCommand`/`finishInsertRecording`: the insert-key handler recorded each typed character for dot-repeat via `command.key`, but a literal space keystroke is normalized upstream to the multi-character token `'<Space>'` (matching real Vim's own key-notation convention, used correctly elsewhere in this same file for the Ex command line at line ~225 and in `packages/vim/parser/index.ts`). The dot-repeat recorder's own `command.key.length === 1` check saw `'<Space>'` (length 8), took the "non-literal key" branch, and set `insertTainted = true` — silently discarding the *entire* insert as a valid dot-repeat target (not just the space), exactly like a real Backspace/arrow-key would, even though the user only typed literal text.

**Fix**: `packages/workbench/vim-session/index.ts`'s insert-key handler now normalizes `'<Space>'` back to `' '` (mirroring the pre-existing pattern at the Ex command line) before the length check, so a space is correctly recorded as one typed character rather than tainting the whole insert.

This is a genuine defect inside T130's already-`done` scope (dot-repeat, `packages/workbench/vim-session/index.ts`), found and fixed as legitimate maintenance while implementing this ticket's own keyboard-only-journey test, not a new T045 feature. It means T130's own prior evidence (`docs/evidence/T130.md`) was itself incomplete: none of its 7 PTY cases happened to insert a space, so the defect went unnoticed there.

**Verified**:

- `tests/e2e/t130-dot-repeat-pty.py` — re-run 3/3 clean after the fix (no regression; none of its existing cases use a space, so this fix was invisible to it, but nothing broke).
- `bun run check` — clean.

- `bun run test:unit` (32/32), `bun run test:services` (28/28), `bun run test:ui` (7/7) — all clean, unaffected (this fix touches only the insert-key dot-repeat recording path).
- `python3 tools/plan.py check` — clean (132 tickets).

**Limitations**: only literal space was found and fixed; other multi-character key tokens (e.g. `'<Tab>'`) are correctly still treated as tainting, since real Vim's own dot-repeat does not replay Tab/Backspace-containing inserts as plain retyped text either — this fix is narrowly scoped to the one character that has a real single-glyph identity but an internal multi-character token representation, not a general rewrite of the taint policy.
