## Observable result

`packages/ui/src/panel-pointer.ts` adds `PanelHitMap` (publishes a frozen, generation-tagged array mapping painted screen row → stable item id) and `installPanelPointerHandler` (attaches `onMouse` to a `Renderable`, resolves `down` events for buttons 0/2 to `{panel, action, itemId, generation, row, column, button}`, and only forwards when the resolved row belongs to the *current* model generation). Explorer, Picker, Search and Problems renderables (`packages/ui/explorer|picker|search|problems/index.ts`) each publish their own `PanelHitMap` from `renderSelf` using the same model instance used for painting, so a row's stable identity can never point at a different item than what was drawn.

`apps/xi/src/main.ts`'s `handlePanelPointer` routes `activate` events: Explorer directories/roots toggle expand-in-place; Explorer/Picker/Search/Problems files call the same open/select paths already used by their keyboard handlers (`openExplorerNode`, `activatePickerEntry`, `openSearchMatch`, `openProblem`), so mouse activation and keyboard activation share one production code path. `context` (right-click) events are intentionally not handled by T127 — they route to `false` and remain T129's responsibility per the T094 split.

Stale-generation protection is structural, not a special case: `PanelHitMap.resolve(row, currentGeneration)` returns `undefined` whenever the caller's live generation no longer matches the generation the row map was published for, which happens on every repaint (item insertion, removal or reordering all bump the model's `generation`). `handlePanelPointer` additionally re-checks `event.generation !== model.generation` before touching selection state, so a click resolved against a stale hit map is a guaranteed no-op even if resolution somehow raced a repaint.

## Failure cases and recovery

- Explorer row inserted beneath a held pointer: covered by `T127-PANEL-02` — `PanelHitMap.resolve` returns `undefined` for the stale generation, and a repaint after the insertion resolves the shifted item correctly by its new row.
- Search/Picker results replaced between press and release: the same generation check in `PanelHitMap` and the redundant `event.generation !== model.generation` guard in `handlePanelPointer` reject the resolved id before any selection/open call executes.
- Explorer directory/root click: does not call `openExplorerNode`; it toggles expand/collapse in place (discovered while writing the Explorer PTY — clicking the already-expanded root row collapses it, which is correct `ExplorerNavigationController.handle('open')` behavior, not a bug, but the PTY fixture had to target child rows specifically).
- Right-click (`action: 'context'`): explicitly returns `false` from `handlePanelPointer`; no context menu exists yet — that is T129, not this ticket.

## Limitations and next action

- Problems-panel row activation shares the identical `PanelHitMap`/`installPanelPointerHandler` wiring as Explorer/Picker/Search (verified by `bun run check`'s type/architecture pass and the same code path used by its keyboard handler, `openProblem`), and now has live-row production PTY proof (`t127-problems-live-diagnostics-pty.py`, see above). The narrative below documents how that gap was closed.

  **Correction to an earlier claim in this document (2026-09-17):** this evidence previously stated "`DiagnosticStore` is constructed but never fed" based on a `grep` that missed a bare-shorthand object property. That was wrong. `apps/xi/src/main.ts:208` **does** pass `diagnostics` (the app's `DiagnosticStore` instance) into `LanguageServerSession`'s constructor options, and `packages/services/language/lifecycle.ts:711` **does** call `this.#options.diagnostics?.publish(...)` on every `textDocument/publishDiagnostics` notification — the wiring itself is real and already exists, contrary to the earlier claim.

  The actual reason Problems stays empty, found by isolating `LanguageServerSession` from the TUI entirely in a standalone probe script: the session's own state machine cycles `starting → initializing → ready → failed` **repeatedly**, with `lastFailure: "Error: language transport operation failed"` — a generic message (`packages/services/language/transport.ts`'s `asErrorMessage` deliberately drops detail for a plain `Error`). It reaches `ready` (the LSP `initialize` handshake succeeds, real capabilities negotiated with the real `typescript-language-server` 5.9.3 binary) but then fails shortly after, before any diagnostics notification is ever received (confirmed: zero diagnostic-model updates fired in the isolated probe across a 20-second window covering multiple full retry cycles).

  Narrowed further with temporary, reverted instrumentation (confirmed via `git diff` showing no residual changes) on two axes:
  - The underlying thrown error, unmasked, is `Error: language server closed its output unexpectedly`, thrown from the transport's own stdout read loop (`transport.ts:229`/`:350`) when the child process's stdout stream ends — i.e., the **`typescript-language-server` child process itself is exiting**, not a bug in Xi's frame/JSON parsing.
  - Logging every outgoing write showed the *exact* message immediately preceding each failure: `{"jsonrpc":"2.0","id":0,"result":[null]}` — Xi's own response to a **server-initiated `workspace/configuration` request** (the server asked for one configuration item; Xi's `configurationResponse` correctly returned a one-element array since no config is loaded, `[null]`). The server's stdout closes immediately after receiving that response.
  - A raw hand-rolled JSON-RPC probe against the same real `typescript-language-server` binary (both via Node's `child_process.spawn` and via `Bun.spawn` directly, bypassing Xi's transport entirely) sent `initialize`+`initialized` and stayed alive the full observation window with no crash — so this is **not** a fundamental Bun/typescript-language-server incompatibility; something specific to Xi's exact message sequence (very likely the `workspace/configuration` response) triggers it, and that response is the one message directly implicated by the logs.

  **The specific hypothesis this pointed to was tested and ruled out.** A second, more careful raw probe advertised the exact same `workspace: { configuration: true, diagnostics: { refreshSupport: true } }` capability Xi does, received the server's real `workspace/configuration` request (`{"items":[{"scopeUri":"...","section":"formattingOptions"}]}`), and answered it with the identically-shaped, correctly-id-matched response (`{"jsonrpc":"2.0","id":0,"result":[null]}`) — and the server did **not** crash; it stayed alive for the full 15-second observation window. So responding to `workspace/configuration` with a one-element `[null]` array is not, by itself, fatal to `typescript-language-server`. The trigger must be something else specific to Xi's fuller session — plausible remaining candidates not yet tested: the much larger full capabilities payload Xi's real `initialize` sends (my probes used a minimal one), a subsequent request Xi's session issues that these probes didn't replicate (e.g. a pull-diagnostics request, or `workspace/didChangeConfiguration`), or a timing/ordering detail.

  This is where the investigation was deliberately stopped: it has moved from "generic transport failure" to "confirmed not a simple configuration-response shape problem, still unidentified," which is a real, honest, useful narrowing for whoever continues it, without pretending a root cause was found when it wasn't. Finding the actual trigger and fixing it is `T123`'s scope ("Route configured language servers through the production CLI"), already flagged by the 06-execution.md G4 audit as an open production-wiring problem for this exact area — continuing to add one more probe variant at a time, indefinitely, would be doing that ticket's work in slow motion under this one's evidence file.

  Panel pointer routing itself is verified correct for whatever rows the read model publishes; there are currently no rows to click in Problems because no diagnostics ever arrive, for the transport reason above — not because the panel-to-store wiring is missing. Re-run an equivalent Problems probe once T123 fixes the transport to close this gap with real rows.

  **Root cause found and fixed (2026-09-17):** the "closed its output unexpectedly" retry-loop symptom was a red herring for the actual blocker. Reading `typescript-language-server` 5.3.0's own source (`lib/cli.mjs`) showed `this.features.diagnosticsSupport = Boolean(publishDiagnostics)`, destructured from the client's advertised `textDocument` capabilities, gating every call to `publishDiagnostics()` (`if (this.closed || !this.features.diagnosticsSupport) { return; }`). Xi's `initializeParams()` in `packages/services/language/lifecycle.ts` never declared `textDocument.publishDiagnostics` at all, so a spec-compliant server correctly concludes the client does not want diagnostics pushed and silently never sends any — independent of whatever separate transport instability produced the earlier "closed its output" symptom.

  Fix: added `publishDiagnostics: {}` to `initializeParams()`'s `textDocument` capabilities in `packages/services/language/lifecycle.ts`, declaring only the minimal, honestly-supported shape (no `relatedInformation`/`tagSupport`/`versionSupport`, since `DiagnosticPublish`/`LanguageDiagnostic` in `packages/services/language/diagnostics.ts` do not model those optional sub-fields).

  Verified end-to-end in production, not just unit-level: `tests/e2e/t127-problems-live-diagnostics-pty.py` spawns the real `bun run apps/xi/src/main.ts` CLI under a PTY with a real `typescript-language-server` child process and a real TypeScript type error (`const value: number = 'not-a-number'`), triggers the (lazy) language session via hover, polls the Problems panel until `XI_PROBLEMS_OPEN` reports `count > 0` (real diagnostics arriving via a real `textDocument/publishDiagnostics` notification — previously impossible to observe at all), then sends a real SGR mouse click at the diagnostic row's production-computed coordinates and confirms `XI_PANEL_POINTER {panel:"problems",action:"activate",...}` fires for that row's stable item id. Passed 3/3 clean runs. This is the exact "diagnostic rows" scenario named in T127's acceptance, and it was not exercisable before this fix.

  This also resolves the earlier concern about the separate `ready→failed` retry loop: with the capability now declared, diagnostics arrive and the session no longer needs to be treated as blocked for Problems' purposes. Whether some other transport instability remains latent under different LSP servers/workloads is still legitimately T123's scope (routing arbitrary configured language servers through the production CLI robustly), not this ticket's — T127 only needed panel pointer routing to work against real rows, which it now does.
