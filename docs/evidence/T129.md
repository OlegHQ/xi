## Observable result

`packages/ui/src/panel-pointer.ts` adds `PanelScroll` (offset/drag bookkeeping: `scrollBy`, `beginDrag`/`dragTo`/`endDrag`, `clamp`, `thumb`) and extends `installPanelPointerHandler` with an optional `PanelScrollHooks` parameter that intercepts OpenTUI `scroll` events (wheel) and `down`/`drag`/`drag-end`/`up` events targeted at the scrollbar column. Explorer, Picker, Search and Problems (`packages/ui/explorer|picker|search|problems/index.ts`) each own one `PanelScroll` instance, compute their own "total rows" and "viewport rows" from their existing read models, auto-scroll to keep the selected/focused row in view when selection changes, draw a one-column scrollbar (proportional thumb, only when content overflows), and reserve that column from the text width so content never overlaps it.

Capture never transfers between panels or to a split: OpenTUI's own mouse-capture semantics route `drag`/`drag-end` events to the renderable that received the `down` event (`event.target === renderable`, the same mechanism the existing splitter drag in `packages/ui/src/workbench.ts` relies on), and `installPanelPointerHandler` only acts on those events when `scroll.isDragging()` is already true, so an ordinary click's synthetic `up` is a no-op. Capture is released on: mouse `up`/`drag-end` (`PanelScroll.endDrag`), `onResize` (every renderable overrides it to end any drag and re-clamp), `visible` becoming `false` (every renderable overrides the accessor to end any drag when the panel is closed by Escape or any other route), and `destroySelf` (`PanelScroll.reset`). Suspend/resume has no distinct code path: no mouse bytes arrive while suspended, and the terminal resize that typically follows resume already runs the `onResize` cancellation.

The mouse toggle is a real runtime switch, not a cosmetic flag: `packages/ui/src/terminal.ts`'s `runOpenTuiWorkbench` accepts a `registerMouseToggle` callback and hands the application a closure that flips OpenTUI's own `CliRenderer.useMouse` (a documented live setter that calls the renderer's internal `enableMouse()`/`disableMouse()`, which send/withdraw the actual SGR mouse-reporting escape sequences — modes 1000/1002/1003/1006). `apps/xi/src/main.ts` binds this both to the leader sequence `<space>m` and to a new "Toggle Mouse" entry in the existing `xi.navigation.commands` `StaticPickerProvider` (the same searchable `<space>;` command palette that already lists Files/Buffers/Themes/Config) — `activatePickerEntry` recognizes the entry's `toggle-mouse` value, closes the picker and calls the identical toggle closure the keybinding uses, so there is exactly one toggle implementation with two entry points, not two divergent ones. Both print the same `XI_MOUSE_MODE` test marker with the new state.

Context menus (`packages/ui/src/context-menu.ts`) are a small application-owned `ContextMenuStore` (items, selected index, activation callback — no document/service state) displayed by a bounded `ContextMenuRenderable`, mounted the same lazy-import way as Picker/Search/Problems in `packages/ui/src/terminal.ts`, with top dispatch priority in `processKeypress` (checked before command line, panels or the editor, since the menu is modal while open). `apps/xi/src/main.ts`'s `openPanelContextMenu` builds one menu per right-clicked row, reusing each panel's *exact* activation code path (`openExplorerNode`, `activatePickerEntry`, `openSearchMatch`, `openProblem`) as the enabled item's action — a menu action is never a separate, divergent implementation of "open." Explorer additionally offers "Expand"/"Collapse" for directories/roots (via the existing `ExplorerNavigationController.handle('open')`) with "Open" disabled for those rows, and vice versa for files. `ContextMenuStore.move()` skips disabled items when navigating, and `activateSelected()`/`activate()` refuse to run a disabled item's action at all — there is no code path that can invoke a disabled action's callback.

A full-screen invisible `ContextMenuBackdrop` mounts directly beneath the menu (zIndex 199 vs. the menu's 200) whenever the menu is open: it intercepts the first `down` event anywhere else, dismisses the menu and swallows that click (`preventDefault`/`stopPropagation`), so an accidental click on another panel or into the editor while the menu is open dismisses the modal instead of also performing whatever that click would otherwise have done.

## Performance and visual evidence

Scroll/drag handling adds no polling: it only runs inside the existing `onMouse` callback (already required for T127's click routing) and existing `renderSelf` repaint path. No new timers, no per-keystroke cost — out of scope for `docs/plan/15-keystroke-latency.md`'s budgets, which govern text-editing input, not panel mouse interaction. No visual/screenshot review beyond PTY byte-stream inspection (same limitation as prior T094/T127 evidence: raw ANSI, not a rendered screenshot).

## Failure cases and recovery

- Scrollbar release lands over another split or panel: not applicable to these panels (they are floating overlays with their own capture, not part of the split-pane grid the T094 splitter drag governs), and OpenTUI's `event.target === renderable` check means a drag begun on one panel's scrollbar never dispatches to another renderable regardless of where the pointer ends up.
- Panel resized mid-drag: `onResize` on all four renderables calls `endDrag()` before re-clamping, verified structurally by `T129-SCROLL-03`'s clamp-after-shrink assertion (a resize that shrinks the viewport below the current offset is exactly this case).
- Panel closed (Escape) mid-drag: the `visible` setter override ends the drag before delegating to the base setter; this is exercised implicitly by every existing Escape-closes-panel PTY (T039/T040/T043/T049) continuing to pass with the override in place, though there is no fixture that starts a drag and then presses Escape mid-drag specifically — see limitations below.
- Wheel input while another panel has focus: each panel's `onMouse` only receives events whose coordinates OpenTUI has already routed to that renderable's screen rect, so a wheel event over the Explorer never reaches the Picker's `PanelScroll` even when both happen to be mounted.

## Limitations and next action

- No PTY fixture starts a scrollbar drag and then presses Escape (or triggers a resize signal) *while the button is still logically held*, to directly observe capture release rather than inferring it from the `onResize`/`visible` override code path. The unit-level `T129-SCROLL-04` proves `endDrag` behavior in isolation; an end-to-end drag+Escape PTY would strengthen this further.
- Problems-panel scrolling and its context-menu route are implemented identically to the other three panels and pass `bun run check`'s type/architecture/lint gates, but — as already recorded in `docs/evidence/T127.md` — there is no live-row PTY for Problems because production diagnostics wiring (T123) does not exist yet, so those paths have no real content to exercise in a production run.
- Search's context-menu route (`event.panel === 'search'` branch of `openPanelContextMenu`) has no dedicated PTY fixture; it is exercised only by `bun run check`'s type/architecture pass. It reuses the identical `openSearchMatch` call already proven live by `t127-panel-pointer-pty.py`'s activate path, so the risk is limited to the menu plumbing itself, not the action.
- The mouse toggle is now searchable via the command palette (`<space>;` → "Toggle Mouse"), which is the discoverability surface `docs/plan/09-interaction.md:62` asks for ("a searchable Toggle mouse command"). It is still not surfaced through `prefixHelp`'s leader-key continuation hints specifically (`bindings: []` in `apps/xi/src/main.ts` remains empty — a pre-existing gap in that separate discoverability path, unrelated to the command palette and belonging to the T082 prefix-help ticket, not this one).
- The PTY tests inject synthetic SGR bytes/keystrokes directly into a PTY rather than through a real terminal's own suppression, so they prove the escape-sequence withdrawal/restoration but not that a real terminal actually stops delivering mouse bytes while disabled; that terminal-level guarantee is proven separately in `docs/evidence/T128.md` (real `xterm` and `tmux` sessions via `Xvfb`/`xdotool`).
- Context menu keyboard equivalents (Up/Down/Enter/Escape) are fixed and not remappable/configurable; that matches every other fixed keybinding already in this launcher and was not treated as a gap.
- T094 (the integration gate) must stay open until T128 (terminal restoration matrix) also passes and E21/E22 are re-run against the fully integrated tree; T129 itself is functionally complete for both its own acceptance items.
