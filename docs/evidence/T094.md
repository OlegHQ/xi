## Observable result

T127, T128 and T129 were implemented and validated in the same shared worktree, not on separate branches — there is no merge step, so "integration" for this gate means two things: (1) confirming the automated suite actually runs every one of those children's fixtures (it did not — see the selector gap below), and (2) exercising a session that combines their features together, including the specific interaction T094's own prior evidence flagged as untested ("cover focus loss/suspend while a splitter drag is active").

**Selector gap found and fixed.** `tools/verify-suite.ts`'s `e2e`/`interaction` selector was a fixed, hand-maintained list that still only named the original T094 fixtures (`t094-controls-pty.py`, `t094-splitter-pty.py`, `t094-terminal-pty.py`) plus older tickets. None of T127's, T128's or T129's PTY fixtures (13 files) had ever been added to it, so `bun run test:e2e -- --suite interaction` — the command every prior evidence file in this ticket family cited as "passed all 24 fixtures" — was **not actually exercising the new work**; those fixtures had only ever been run manually, one at a time. Fixed by adding all 13 fixtures (`t094-integration-pty.py`, both T127 panel-pointer fixtures, the live-diagnostics fixture, all five T128 named-terminal/xterm fixtures, and all four T129 fixtures) to the `interaction` selector. The suite now runs 37 fixtures, not 24.

**New integration fixture: `tests/e2e/t094-integration-pty.py`.** One production session that, in order: opens the Explorer sidebar and wheel-scrolls it (T129, and confirms the panel wheel path does not leak into the editor's own `XI_POINTER_SCROLL` marker); right-clicks a row to open a context menu and dismisses it with Escape (T129); activates a file by stable item id through the Explorer (T127); toggles mouse mode off via the leader keybinding and confirms a subsequent click produces no marker at all, then re-enables it and confirms clicks work again (T129); creates a split (`:vsplit`) and begins a live splitter drag; sends a **real `SIGTSTP`** while that drag is live and confirms the process actually stops (`/proc/<pid>/status` state `T`) and the drag is cancelled (`XI_WORKBENCH_SPLITTER {"action":"cancel",...}` plus `XI_POINTER_CANCEL {"reason":"suspend"}`); sends **`SIGCONT`** and confirms the process resumes and a fresh splitter drag afterward begins and commits cleanly (proving capture state was not left corrupted by the suspend); then edits, saves and quits with exact bytes verified against the file that ended up active.

This closes T094's own previously-recorded gap verbatim: earlier evidence in this file listed "cover focus loss/suspend while a splitter drag is active" as unaddressed, and no other ticket's evidence (T127/T128/T129) exercises a live drag interrupted by a real process-level suspend signal — T128's fixtures qualify suspend/resume and splitter drag as separate capabilities, never combined in one session.

## Failure cases and recovery

- Live splitter drag interrupted by suspend: previously untested combination; now proven to cancel cleanly (`action: "cancel"`, `reason: "suspend"`) rather than hang or leave the drag capturing after resume.
- Panel wheel scroll leaking into the editor's own scroll path: checked explicitly (`XI_POINTER_SCROLL` must not appear from a panel-scoped wheel event) and confirmed absent.
- Context menu left open across an unrelated action: checked by dismissing with Escape before proceeding, consistent with T129's own backdrop-dismiss coverage.
- All other failure cases (stale generation, disabled-action rejection, crash while mouse modes enabled, unsupported fish/tmux configuration) are covered in T127/T128/T129's own evidence and are not re-derived here.
