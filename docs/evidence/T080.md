## Observable result

`replayVimMultiDot` validates one current document version and complete selection set, resolves the stored semantic target once against that set and leaves repeat state unchanged until the caller commits success. Recipes contain motion/operator or insertion semantics rather than old offsets. Failed or incompatible replay, stale selections and invalid counts publish no target change. Service events preserve the prior successful target, while a successful insert replaces it; explicit counts apply to every member through the shared resolver.

## Performance and visual evidence

No rendered UI budget applies to this pure repeat-state resolver. It stores bounded semantic values and performs no process/filesystem work; editor rendering and interactive latency are downstream qualification work.

## Failure cases and recovery

No target, stale document/selection generations, invalid counts and incompatible recipes return typed failures before replay. Service, yank, undo and interrupted-insert events retain the prior target and sequence. Selection creation is not a repeat event.
