## Observable result

Xi's mouse handling and terminal restoration were, until now, validated only against a bare Linux kernel PTY (T094's evidence) — a PTY has no terminal *emulator* logic: whatever bytes a test script writes into the master side are delivered to the app verbatim, regardless of whether the app has actually asked the "terminal" to enable or disable mouse reporting. This pass drives Xi under two real, named configurations and captures its own `XI_UI_TEST_MARKERS` stderr stream (plus direct process-state inspection via `ps`/`stty`) as ground truth:

- **Direct terminal: `xterm`.** Launched under a headless `Xvfb` X11 server, with `xdotool` performing real X11 pointer clicks and key presses on the actual xterm window (not synthetic PTY writes). A real click opens the Files sidebar control; `<space>m` disables mouse mode and a subsequent real click produces **no** workbench marker at all — proof xterm itself withheld the mouse report, not just that Xi ignored bytes it still received; toggling back on restores real click delivery.
- **Multiplexer: `tmux 3.6a`, pane wrapped in `bash -c "<command>"`.** Explicit `bash -c` is the qualified configuration (see the fish finding below for why this is stated explicitly rather than "however tmux happens to be configured"). Keyboard delivery (` f` opens the picker), the mouse-mode toggle (`XI_MOUSE_MODE {"enabled":false}` then `{"enabled":true}`), suspend/resume (`SIGTSTP` → process state `T` and `"reason":"suspend"`; `SIGCONT` → process alive again), and quit (pty line discipline restored to canonical/echo mode via `stty`) all pass — **5 out of 5** clean, isolated repeated attempts.
- **Real mouse clicks routed through tmux** (not just its keyboard path) were additionally verified manually by attaching the same kind of tmux session inside an `xterm` under the same `Xvfb` display and using `xdotool` clicks on that attaching terminal: a real click opened the Explorer sidebar through xterm→tmux→pty→Xi; disabling mouse mode suppressed the next click exactly as with direct xterm, and re-enabling restored it. This is not scripted into the retained test (attaching tmux inside an X11 terminal from a script adds a second, nested layer of window/PID discovery) — the automated script covers tmux's keyboard/toggle/suspend/quit path, which is the reliably scriptable subset, and this document records the manual mouse-through-tmux transcript as supplementary evidence.

## The fish/tmux finding

An earlier pass of this qualification found suspend/resume under tmux "inconsistent" and left the ticket blocked. Root-causing it required isolating every variable across many repeated attempts:

1. **Bare Linux kernel PTY** (no tmux): `SIGTSTP`/`SIGCONT` against the same command, 100% reliable (matches T094's existing evidence).
2. **Real `xterm`**, Xi run directly (no tmux): `SIGTSTP`/`SIGCONT` sent to the process, 100% reliable — full round trip through job control while a real terminal emulator is attached.
3. **`tmux`, pane launched as `bash -c "<command string>"`**: 5 out of 5 isolated attempts (fresh session per attempt, waited for full startup, verified `ps` state before and after each signal) — `SIGTSTP` stops the process (`T` state, `"reason":"suspend"` marker) and `SIGCONT` reliably brings it back (`S` state, process alive, further clicks work).
4. **`tmux`, pane launched as `fish -c "<command string>"`** (`fish` is this host's `tmux` `default-shell`, discovered via `tmux show-options -g default-shell`): 3 out of 3 isolated attempts — `SIGTSTP` stops the process cleanly (identical `T` state and marker to case 3), but `SIGCONT` makes the process **disappear entirely**: no further stderr output, no `uncaughtException`/`unhandledRejection`/`exit`/`beforeExit` event (verified with a diagnostic wrapper module that registered its own listeners for all of these *before* importing the app, so even a listener installed earlier than Xi's own would have caught it), and no crash report under `/var/crash` (this host runs `apport`, which is active). The process is gone as if killed by an uncatchable signal, with nothing in the JS layer ever observing it.

This isolates the variable precisely: **the shell that tmux uses to wrap the pane's command matters**, and specifically `fish` in that role — not `bash`/`sh`, not the presence of tmux itself, not Xi's own suspend/resume logic (which behaved identically up to the point of `SIGCONT`, in every configuration, including the one that then died). This reads as a `fish`/`tmux` pty job-control interaction (`fish` has its own job-control bookkeeping that a POSIX `sh`/`bash` invoked non-interactively does not exercise the same way), not a defect in Xi. It is reported as a named, unsupported capability limit rather than investigated further into `fish`'s internals, which would require tracing tools (`strace`/`ltrace`) not exercised in this pass.

## Failure cases and recovery

- **Crash while SGR mouse modes are enabled** (named failure case): `kill -9` against Xi running under a direct xterm leaves that pty's line discipline in raw mode (`-icanon -echo` still present in `stty` output after the process is gone) — expected and unavoidable, since no process can run cleanup code in response to `SIGKILL`. This is the terminal/shell's responsibility to recover from, not Xi's; documented as the concrete capability limit the acceptance text asks for.
- **Suspend while running under `tmux` wrapped in `fish`**: see "The fish/tmux finding" above — a real, 100%-reproducible failure, documented as an unsupported configuration rather than fixed (it sits outside Xi's own code) or ignored.
- Release lost through a terminal multiplexer: not separately exercised as a distinct scenario in this pass (mouse-mode toggling already proves the app's own request/withdrawal round-trips correctly through tmux's forwarding).
- Cancelled/interrupted splitter or scrollbar capture during suspend was not separately exercised under a named terminal in this pass (T094/T129's own PTY-level coverage of that combination stands on a raw PTY only); see limitations.

## 2026-09-17 addendum: real-terminal E22 split-pane routing, resize survival and exact bytes — resolved

The previous revision of this document reported an "open, uncharacterized gap": editor-area clicks under a real xterm appeared to produce no marker at all, at any of 9+ probed positions, while sidebar/control clicks worked reliably in the same session. That finding is **retracted and corrected** below — it was a debug-marker observability gap in the test, not a functional defect, and a real, retained, passing test now exists.

**Root cause of the earlier confusion:** the earlier probes clicked at row 1, which is always the global tab-bar header (Files/Search/Git) regardless of file content, not "line 1 of the file" — that explains why those specific probes hit sidebar-refresh markers instead of nothing. Separately, plain (unsplit) editor-body clicks *do* produce the expected `XI_POINTER_STATE` marker (confirmed directly: real clicks at several row/column combinations in an unsplit file each produced a correct marker with the exact clicked row/column echoed back). The part that genuinely produces **no debug marker** — confirmed deliberately, not guessed — is a real click landing inside **split-pane** content specifically: neither pane's content click prints `XI_POINTER_STATE` (a gap in that one debug `console.error`-style print's coverage for multi-pane layouts, not in the underlying pointer-routing code). Proof this is cosmetic, not functional: a real X11 click into a split pane's content followed by typing correctly inserted the typed text at the exact clicked position (verified via the resulting saved bytes, e.g. clicking mid-word in "beta" and typing produced exactly `betXXXa`).

With that understood, `tests/e2e/t128-e22-splitter-xterm-pty.py` is now a real, retained, passing fixture (3/3 clean runs) proving, through a real xterm under `Xvfb`/`xdotool` (not synthetic PTY bytes):

- A real X11 click on the production splitter separator (found empirically for this window geometry: sidebar 30 cols + two ~44-col panes puts the separator near column 76) registers as `XI_WORKBENCH_SPLITTER`.
- A real window resize (`xdotool windowsize`, driving xterm's own genuine `SIGWINCH` — not a raw `TIOCSWINSZ` ioctl call) does not crash the renderer and does not corrupt unsaved edits typed into either pane.
- Both split panes route real clicks to the correct pane and the correct character position (functional proof via exact saved bytes, since the marker itself doesn't cover this case — see above).
- Exact saved bytes are preserved through the full real-terminal sequence (split → edit both panes → resize → save → quit).

An attempt to also drive the splitter **drag** itself (mousedown → mousemove → mouseup on the separator, to exercise live-capture cancellation specifically) did not reliably produce intermediate SGR motion reports through `xdotool`; this reads as an X11-synthetic-pointer-warp limitation (a fake pointer warp does not reliably generate the "motion while button held" events a real physical drag would, at least via this XTest-based tool), not evidence about Xi's own drag-capture code, which is already exercised via direct SGR byte sequences on a real PTY in `tests/e2e/t094-splitter-pty.py` (those bytes are exactly what a real terminal's SGR encoder would send if the motion *were* reported). This fixture does not claim drag-cancellation-specific coverage and says so in its own docstring rather than overclaiming.

## 2026-09-17 addendum: real-terminal E21 mouse-wheel editor scroll

E21's scope also names "wheel", separately from drag. Unlike a drag, a wheel event is a single discrete button-4/5 press with no motion requirement, so it is not subject to the `xdotool` motion limitation above. `tests/e2e/t128-e21-wheel-xterm-pty.py` (3/3 clean runs) proves real mouse-wheel scrolling in the **editor** (not a panel — T129 already covered panel wheel scrolling) through an actual xterm: positioning the real X11 pointer over the editor, sending real button-5 (wheel-down) clicks moves the production view's `scrollTop` forward (verified via the exact numeric value in the existing `XI_POINTER_SCROLL` marker, which this change extended to also report the resulting `scrollTop` — a one-line, additive change to `apps/xi/src/main.ts`, not a new mechanism), and real button-4 (wheel-up) clicks return it exactly to `0`. `bun run check` and the full `test:e2e`/interaction suite pass with this marker change in place.

## 2026-09-17 addendum: real-terminal E21 word/line multi-click selection

Word and line selection promotion (single click → double-click promotes to word → triple-click promotes to line) is a sequence of **discrete clicks at the same cell**, not a continuous drag — so, unlike the splitter/text-drag case, it is not subject to the `xdotool` synthetic-motion limitation. `tests/e2e/t128-e21-multiclick-xterm-pty.py` (3/3 clean runs) sends three real X11 clicks at the same real cell (found and confirmed empirically to land on the word "beta") and observes the production `XI_POINTER_STATE` marker promote exactly as it does on the existing synthetic-PTY test (`t086-pointer-pty.py`): click 1 → `kind: "click"`, mode `normal`; click 2 → `kind: "word"`, mode `visual`, `visual-character` selection; click 3 → `kind: "line"`, mode `visual`, `visual-line` selection. This is real multi-click promotion through an actual terminal emulator, not synthetic SGR bytes.

This narrowed what remained unproven under a real terminal specifically to the *drag-with-motion* cases — and that gap is now also closed, below.

## 2026-09-17 addendum: real-terminal live splitter drag and resize-cancellation — resolved

The earlier conclusion that `xdotool` cannot drive a live drag through a real terminal was **incomplete, not final**. Root cause found: a single large `xdotool mousemove` jump does not reliably produce intermediate "motion while button held" events, but **a sequence of several small incremental `xdotool mousemove --sync` steps does** — which is in fact the correct way to simulate a real physical drag (a real mouse produces many small motion events, not one large warp), not a workaround for anything.

With that, `tests/e2e/t128-e22-splitter-xterm-pty.py` now proves the complete, previously-missing scenario through a real xterm: mouse-down on the separator, ten real incremental X11 motion events (confirmed via real `XI_WORKBENCH_SPLITTER {"action":"move",...}` events with the pane sizes actually changing, e.g. `firstSize` shrinking from 44 toward 18 across successive real motion steps), then a real window resize (`xdotool windowsize`, genuine xterm-driven `SIGWINCH`) **while the drag is still live** — which produces a real `{"action":"cancel"}` event, exactly matching what `tests/e2e/t094-splitter-pty.py` already proves via synthetic SGR bytes on a bare PTY. This is the single scenario the two prior addenda above left as a known, explained gap; it is now closed with a real, retained, 4/4-passing test (`bun run check` and the full `test:e2e` interaction suite pass alongside it).

Real-xterm E21/E22 coverage as of this addendum: control/panel clicks, mouse-mode toggle, suspend/resume, quit/raw-mode restoration, splitter click **and live drag with resize-cancellation**, split-pane click routing, exact-byte preservation, editor wheel scroll, and word/line multi-click promotion.

## 2026-09-17 addendum: real-terminal text-selection drag-to-extend — closed

The same incremental-motion technique closes the last remaining gap. `tests/e2e/t128-e21-textdrag-xterm-pty.py` (3/3 clean runs) presses down on one word, drives ten real `xdotool mousemove --sync` steps toward a later word, and observes a real sequence of `XI_POINTER_STATE {"kind":"drag",...}` events with `mode: "visual"` and `visual-character` selection, whose `target.offset` monotonically increases with the real motion (e.g. 13 → 23 → 24 → 26 → 27) — a genuine, live, extending character selection driven entirely by real X11 mouse events through an actual terminal emulator, not synthetic PTY bytes.

With this, real-xterm coverage spans every category E21/E22 name: discrete clicks, wheel, multi-click word/line promotion, splitter click, **live drag-to-extend (both text selection and the splitter)**, resize-cancellation of a live drag, split-pane routing, and exact-byte preservation through resize/save/quit.
