## Observable result

The spike renders synthetic visible rows through a disposable custom OpenTUI `Renderable`; it has no editable widget store or document buffer. It enables OpenTUI's retained buffer, tracks dirty row spans, and paints only dirty rows into that buffer. For a one-cell edit, OpenTUI's native output diff changed one terminal cell and wrote 84 bytes at both target sizes, while retaining all other visible rows. Cursor-only movement changed zero text cells. The adapter converts the fixture's zero-based row/column to the one-based coordinates required by `RenderContext.setCursorPosition`.

The probe uses only public OpenTUI APIs. It covers initial render, dirty spans, cursor, resize, Unicode, renderer disposal, mock key input, and captured output. Separate xterm screenshots and kernel PTYs exercise the real CLI renderer and terminal lifecycle.

## Performance and visual evidence

Each target size ran 120 public mock keypress events through the event handler, one-cell mutation, OpenTUI render loop, and captured output. These are local prototype measurements, not a release budget or comparison against a baseline revision.

| Viewport | Initial frame | One-cell update | Input-to-output p50 / p95 / p99 / max | Mean output per event |
|---|---:|---:|---:|---:|
| 120x40 | 6,527 bytes; 4,800 cells | 84 bytes; 1 cell | 0.1074 / 0.2124 / 0.4946 / 2.0556 ms | 88 bytes |
| 240x70 | 19,787 bytes; 16,800 cells | 84 bytes; 1 cell | 0.2037 / 0.2452 / 0.2755 / 0.4051 ms | 89 bytes |

The raw per-event JSON records latency, output bytes, native cells updated, native render time, and native stdout-write time. The summary also records process CPU usage and before/after RSS as local diagnostics; those values are not used as acceptance thresholds. No cross-revision baseline or release performance budget was specified by T002.

Screenshots were captured from the actual OpenTUI CLI renderer running inside xterm at both target geometries. Visual review found the full synthetic viewport visible, the cursor at its requested logical cell, the right-edge glyph confined to the viewport, and the following row intact. The screenshots use a single recorded font and Xvfb environment; they do not establish cross-terminal or cross-font parity.

## Failure cases and recovery

- `t002-wide-glyph-right-edge-120x40` and `t002-wide-glyph-right-edge-240x70`: a two-cell emoji follows `width - 1` ASCII cells. Captured display width equals the viewport and row 1 matches its pre-test contents. The actual xterm frames also show the following sentence intact.
- `t002-failure-resize-backpressure-01`: a held Node `Writable` callback creates observable output backpressure. Resize occurs while `writableNeedDrain` remains true. After release, dimensions and the in-flight edit are present in the final frame.
- `t002-close-error-01`: injected render failure is delivered, then renderer and viewport are destroyed and native allocator activity returns to baseline.
- Real PTY close and error scenarios: terminal raw mode and alternate-screen/cursor state are restored; each child exits successfully.
- Screenshot review found and corrected a one-cell cursor offset at the `RenderContext` boundary. The viewport keeps zero-based coordinates and passes one-based terminal coordinates to OpenTUI; the regenerated captures and cursor probe pass.

## Limitations and next action

No T002 acceptance item remains unmet. This is an isolated renderer prototype over synthetic rows, not document-package integration or Vim editing. The measurements are exploratory and have no baseline or release threshold. Continue production UI work under the document ownership and typed-port boundaries in the architecture specification; do not treat the fixture row model as application storage.
