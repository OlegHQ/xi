## Observable result

Before this ticket, Xi had exactly one runtime theme (`LIGHT_WORKBENCH_THEME`, hardcoded), and the picker's `'theme'` mode had one static entry with no `activatePickerEntry` branch at all — selecting it did nothing.

This pass adds a second real built-in theme (`DARK_WORKBENCH_THEME`, `packages/ui/src/workbench.ts`) and a live theme-switching mechanism for `WorkbenchRenderable`:

- `WorkbenchRenderable.setTheme(theme)` (new public method) reassigns the renderer's cached theme-derived colors and forces a full repaint on the next frame.
- `packages/ui/src/terminal.ts` gained a `registerThemeSwitch` option (mirroring the existing `registerMouseToggle` pattern) so the host application can obtain a live `setTheme` callback.
- `apps/xi/src/main.ts` wires this into the file/theme picker's existing preview/commit/cancel flow: navigating to a theme entry (or opening the picker, since it auto-previews its top result exactly like the file picker already does) calls `setTheme` immediately (live preview); Escape reverts to the theme active before the picker opened; Enter commits it (keeps it, clears the revert-on-cancel state).

**A genuine pre-existing rendering bug was found and fixed while building this**: `WorkbenchRenderable.renderSelf`'s full background/sidebar/header repaint is gated behind a `fullRepaint` flag that only becomes true when the terminal's width/height actually changes (`#lastShellSize` comparison) — a theme change alone left `fullRepaint` false, so `setTheme`'s `requestRender()` call scheduled a frame that then silently skipped repainting the background/sidebar/header entirely (confirmed empirically: the dark background color never appeared in the real terminal stream despite `setTheme` genuinely being called with the correct theme object). Fixed by also clearing `#lastShellSize`/`#lastHeaderText`/`#lastStatusText` inside `setTheme`, forcing the same full-repaint path a real resize already takes.

## Failure cases and recovery

- Cancel (Escape) after a live preview correctly reverts via the same `setTheme` mechanism, verified in the retained fixture.
- An unregistered `setTheme` callback (e.g. if `registerThemeSwitch` is never wired by a composition root) makes `previewTheme`/commit a safe no-op (`setWorkbenchTheme?.(...)`), not a crash.

## 2026-09-17 (later still): real cross-launch persistence for the committed theme

Implemented a **deliberately minimal, scoped** persistence mechanism — not the general config-load pipeline `apps/xi/src/main.ts` still doesn't have (confirmed absent again during this pass; that remains separate, larger scope). New helpers in `apps/xi/src/main.ts`: `themeStatePath()` (`~/.config/xi/state.json`, the standard XDG-style convention, resolved via `process.env.HOME` — the same variable every PTY test in this suite already sets, so behavior is directly testable), `readPersistedThemeId` (best-effort; a missing/corrupt/unreadable file never blocks startup, returns `undefined` and falls back to `xi-light`), and `writePersistedThemeId` (creates the directory via the existing `filesystem.makeDirectory` port, then `filesystem.writeFileAtomic` — both real platform-port calls, not a bypass of the architecture's ownership rules).

Wiring: `OpenTuiWorkbenchOptions` (`packages/ui/src/terminal.ts`) gained a `theme` startup option, threaded into `WorkbenchRenderable`'s construction so every renderable surface paints correctly from its very first frame (no startup flash of the wrong theme, since `currentTheme` — already used to theme lazily-constructed panels — now reads the real persisted value via the existing `viewport.theme` getter). `main.ts` reads the persisted theme id before constructing the workbench and resolves the correct `WorkbenchTheme` for that first frame; committing a theme (Enter in the picker) now also fires a best-effort, non-blocking write to the state file.

Verified by extending `tests/e2e/t132-theme-switch-pty.py` once more (3/3 clean runs): after the full preview/cancel/commit/token-consistency flow, the test quits and launches a **second, entirely fresh process** against the same `HOME`, and confirms it starts dark immediately — with zero picker interaction — proving the round-trip through the real filesystem, not an in-memory assumption. ## 2026-09-17 (final): theme.toml custom theme loading closes the last acceptance item — T132 passes

**Implemented, with one real naming-convention correction caught before it shipped.** New `apps/xi/src/main.ts` machinery: `workbenchThemeFromTokens` (builds a full `WorkbenchTheme` from a parsed `ThemeConfig.tokens` table, requiring every core field explicitly — `background`/`surface`/`surface.active`/`foreground`/`muted`/`border`/`accent`/`error` — so a theme missing any of them is rejected outright, never partially applied) and `discoverCustomThemes` (lists `~/.config/xi/themes/*.toml`, parses each with the real `parseThemeConfig` via a new lazy entrypoint `packages/services/src/entrypoints/theme.ts`, and reports a clear, file-named `stderr` message for anything invalid — a missing directory is the ordinary "no custom themes" case, not an error). Discovered themes are merged into the same `WorkbenchTheme` registry the two built-ins live in, appear in the picker with their own `theme.toml`-declared display name, and go through the identical preview/cancel/commit/persist flow already built for `xi-light`/`xi-dark` — no separate code path for custom vs. built-in.

**The correction**: the first implementation invented its own flat, camelCase token names (`background`, `surfaceActive`, …). Before finalizing, cross-checked against `packages/services/config/index.ts`'s own `DEFAULT_THEME_TOML` and `tests/config/t036-config.test.ts`, which already establish a dotted, lowercase convention for the optional editor-layer tokens (`selection.primary`, `cursor.primary`, `motion.trail`, `operator.preview`) — a convention my first pass ignored and would have shipped as a second, incompatible naming scheme in the same codebase. Renamed `workbenchThemeFromTokens` to use `surface.active` and the four existing dotted names for the optional fields, extending the same dotted style (not previously defined) for the other required core fields, so every `theme.toml` in the project now follows one consistent convention.

**Verified with a new production PTY test** (`tests/e2e/t132-custom-theme-pty.py`, 3/3 clean runs): seeds `~/.config/xi/themes/` with one genuinely valid custom theme (`neon.toml`, using the corrected dotted token names) and one invalid one (missing its `[tokens]` table entirely); confirms the invalid file never blocks startup and is rejected with a specific, file-named `stderr` message; confirms the valid theme appears in the picker and previews live with its own real, distinct color (checked via actual terminal SGR bytes); then — covering T132's own explicitly named failure case "Theme file removed from disk after being selected" — removes the just-committed custom theme's file and relaunches a fresh process, confirming a graceful fallback to the light theme with no crash and no stale/partial custom colors. T132's third named failure case ("Cancel after multiple preview navigations restores the original theme exactly") was verified with a throwaway probe (multiple arrow-key navigations before Escape still restores the original theme exactly) — this is structurally guaranteed by `themeBeforePicker` being captured once at picker-open and reverted once on cancel regardless of navigation count, so a dedicated retained fixture was judged unnecessary on top of that direct code-level guarantee plus the manual confirmation. "theme.toml with a missing or malformed token" (the first named failure case) is covered by this new fixture's `broken.toml` (missing) combined with the pre-existing, already-passing `tests/config/t036-config.test.ts`'s `T036-FAIL-THEME-01` (malformed hex value) — the same `parseThemeConfig` this ticket newly calls from production code for the first time.
