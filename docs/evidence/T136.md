## Input correctness blocker resolved

The T135 50-of-80 movement failure was not dropped burst input. Instrumenting Core
keypress delivery, workbench dispatch and Vim parsing showed 51 `j` commands (including
the first-key probe), but 30 lowercase `down` events failed as `unknown-key`. The shared
workbench `keyName` adapter translated Escape/Return but omitted Core's named arrows.
The final 30 burst j keys worked, reaching row 50 after the initial 20 j keys. Earlier
cumulative observations incorrectly attributed those final movements to held arrows.

The adapter now canonicalizes named keys case-insensitively while preserving printable
key identity and modifier handling. No engine motion or React input semantics changed.
`tests/workbench/vim-session-terminal-keys.test.ts` feeds real terminal byte sequences
through the pinned Core StdinParser and the owned Vim session. It compares exact text,
cursor and mode against clean pinned Neovim using queued feedkeys, checking the oracle
binary SHA256 from the manifest. It covers Normal, Visual and Insert arrow use plus
uppercase G. Oracle: Neovim 0.12.4, no personal configuration.

Executed:

- `bun tests/workbench/vim-session-terminal-keys.test.ts` — pass, four oracle fixtures.
- `bun tests/workbench/vim-session-text-objects.test.ts` — pass, 19 neighboring checks.
- `bun tests/ui/t111-render-scheduling.test.ts` — pass, including asynchronous ordering,
  in-flight invalidation and held output backpressure.
- `bun run check` — pass; `.artifacts/ui-opt/check.log`.

Diagnostic-only instrumentation and failed reproductions are retained under
`.artifacts/ui-opt/trace*` and `burst-probe/`. They are not timing measurements.
One initial uppercase J oracle fixture exposed a separate unsupported owned-session
join operation. It was not used to qualify J; the focused adapter regression uses
supported G to check preservation of uppercase semantics. J remains a separate parity gap.

## Measurement producer correction

`bench/performance/ui-proof.py` now uses an independent, persistent input process
prepared before application startup. Timed output is captured with PTY arrival timestamps
and parsed afterward. Only verified cumulative text/cursor state completes an event;
output predating that event's write cannot satisfy it. Scheduled delivery, actual writes,
correct-output arrival, first key, paced motions, held arrows and bursts remain separate.
Three parser regressions cover software/hardware cursors, synchronized updates, wide
cells and orphan wide-cell continuations. Files must match exact final Unicode bytes.

The optional `--neovim` baseline verifies the pinned binary hash and runs clean, idle
Neovim with the same file, terminal size and input schedule. It does not claim equivalent
loaded-service coverage: the real Xi task-output load applies only to Xi variants.

Historical attempts remain retained. The old threaded producer's parsing cost distorted
injection and completion timestamps. A per-batch process corrected that but added Python
launch delay to first-key injection. The persistent producer removes that avoidable
measurement overhead. The old load heartbeat also had a truncate/read race: publication
now uses atomic replacement and empty text is no longer silently treated as zero.
A pyte display failure on an orphan wide-cell continuation is handled explicitly and has
a regression. None of these corrections removes burst inputs or weakens product budgets.

Reproduction (fresh output path required, compiled candidates prepared separately):

```sh

uv pip install --python .artifacts/ui-proof/venv/bin/python -r bench/performance/ui-proof-requirements.txt

  --binary core=/absolute/path/to/core-cli --binary react=/absolute/path/to/react-cli \
```

Source/binary hashes, per-session events and percentiles, memory snapshots, raw ANSI,
parsed screens and failures are retained. These are shared-host diagnostics: no physical
latency, CPU/GC/allocation qualification, large-file coverage, or complete migrated UI.

## Retained optimization and final comparison

Shipping builds now use `--minify`, a compile-time `process.env.NODE_ENV="production"`
and `process.env.DEV="false"`. The package script, release builder and compiled PTY
fixtures use identical flags. Source development remains unchanged. The experimental
comparison builder applies the same settings to Core and React, with a third production
React binary disabling only minification. No UI feature is disabled or deferred past the
first usable frame. The real React status surface is mounted before the editor starts.

Production mode alone reduced memory somewhat but did not show a clear startup benefit
in its 60-journey comparison. An import/native-initialization overlap experiment showed
no repeatable gain and was removed. No custom module loader, dependency fork or new
render scheduler was retained. Historical comparisons are under `production-comparison/`
and `overlap-comparison/` in `.artifacts/ui-opt/`.

Final command:

```sh
XI_UI_PROOF_OUTDIR=.artifacts/ui-opt/final bun spikes/ui-react/build-cli.ts
.artifacts/ui-proof/venv/bin/python bench/performance/ui-proof.py \
  .artifacts/ui-opt/paired-verified \
  --binary core=.artifacts/ui-opt/final/xi-core \
  --binary react=.artifacts/ui-opt/final/xi-react \
  --binary react-unminified=.artifacts/ui-opt/final/xi-react-unminified \
  --neovim .artifacts/oracle/nvim-linux-arm64/bin/nvim --sessions 12 --load both
```

**84/84 journeys passed, 10,164 verified key completions.** There are 12 independent
processes and 1,452 keys per condition. The deterministic random order uses seed 135;
fixture is 400 normal ASCII lines, with Unicode inserted during the workload, at 120×40.
Every journey checks exact saved bytes, including all held-arrow and burst events.
Task conditions verify an actual output-producing task remains active during measured
editing. First-key samples precede task launch in both idle and task conditions; they
are startup/first-key samples, not loaded-first-key qualification.

usable cells, including initial parsing cost; 12 samples cannot establish robust tails.
No calibrated reference-host pass is claimed.

Minification reduced idle React startup p50 by **15.07 ms**, about 14%, in this run.
Pairing by session, the median startup difference is −11.22 ms; a simple 10,000-resample
paired bootstrap (seed 136) gives a diagnostic 95% interval of −26.34 to −3.48 ms.
The loaded pairing is noisier: −7.90 ms, interval −16.53 to +10.98 ms. Do not claim a
statistically established loaded startup improvement or a general Neovim startup win.
React still adds **9.54 ms idle startup p50** over optimized Core in this comparison.

React executable size fell **145.63 → 136.75 MiB**; optimized Core is 133.56 MiB.
RSS snapshots fell 6.77 MiB idle and 14.76 MiB loaded compared with unminified React.
These are post-journey snapshots affected by GC/workload timing, not proof of allocation,
retained-native-memory or peak-process budgets. React's lower loaded snapshot than Core
must not be interpreted as negative React overhead.

## Latency findings — not a pass

Actual PTY write to captured output later verified to contain correct text/cursor state,
pooled over the 1,452 keys per condition:

| Variant | Load | p50 / p95 / p99 / max (ms) |
| --- | --- | --- |
| Core minified | idle | 2.14 / 5.68 / 12.23 / 15.01 |
| React minified | idle | 1.99 / 5.33 / 11.33 / 14.95 |
| React unminified | idle | 2.07 / 5.66 / 9.20 / 12.02 |
| Core minified | task | 1.96 / 5.99 / 10.52 / 14.53 |
| React minified | task | 1.78 / 4.61 / 8.06 / 18.49 |
| React unminified | task | 1.81 / 4.56 / 6.95 / 13.19 |
| Clean Neovim | idle | 0.35 / 0.93 / 1.48 / 2.37 |

Pooling hides failures. The actual per-action p95 values are:

| Action | Core idle | React idle | Core task | React task | Neovim idle |
| --- | ---: | ---: | ---: | ---: | ---: |
| First key (before load) | 12.23 | 14.33 | 12.24 | 18.49 | 0.43 |
| Paced j | 2.70 | 2.62 | 2.87 | 2.74 | 0.94 |
| Held Down | 3.84 | 3.60 | 4.30 | 4.16 | 1.05 |
| Burst j | 6.07 | 6.82 | 6.19 | 4.55 | 0.75 |
| Paced Unicode insertion | 4.09 | 4.06 | 3.99 | 3.55 | 0.79 |
| Burst Unicode insertion | 13.65 | 8.30 | 8.77 | 5.37 | 1.15 |

First-key latency and some burst families exceed the mandatory 8 ms p95. Idle React's
pooled p95 exceeds Neovim by 4.40 ms, above the ≤3 ms overhead requirement; per-family
comparisons also fail. Core alone already has first-key/burst failures. This supports
keeping the viewport and engine independent of React, but does not certify replacing
the whole UI or excuse either implementation's failures.

Scheduled delivery must not disappear from the report. Scheduled-to-correct p95/max are
29.32/75.94 ms Core idle, 23.42/109.21 ms React idle, and 29.77/79.14 ms Neovim idle.
Input-injection slippage p95/max is respectively 25.25/72.16, 20.11/106.72 and
29.22/78.65 ms. Loaded React scheduled-to-correct p95/max is 5.11/18.70 ms, with
0.30/10.88 ms injection slippage. Large idle slippage also occurs in the clean oracle;
its cause is not established. It is not evidence of a React stall. A qualified host and
independently calibrated producer are still required; no timers, busy-spins or warm-up
traffic were added to hide these observations. No Xi-attributable ≤8 ms stall guarantee
has been established.
