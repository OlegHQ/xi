## Observable result

The user's command, `bun run apps/xi/src/main.ts`, uses the fork through a Bun dependency patch stored in the pinned submodule. The baseline OpenTUI import took 144.04 ms in an isolated CPU profile. Native `dlopen` accounted for 86.2 ms self time; the complete FFI setup subtree took 90.4 ms. Parsing took 20.6 ms self time and module linking/declaration work another 7.7 ms. These are sampled attribution values, not independent additive stopwatch measurements.

The library eagerly bound 423 native symbols, including 41 audio symbols. An isolated binding experiment measured 89.82 ms for all 423 versus 1.06 ms for one. The fork opens one initial binding/callback owner, resolves other symbols on access, and caches the direct backend function. No function, syntax service, editor feature or native asset is removed. Resolving all 423 functions still works; a subsequent diagnostic measured 2.38 ms initialization and 96.67 ms to force all remaining bindings.

For Bun executables on Unix, the native asset is materialized once into a private process-owned file so deferred bindings share native state. Normal process exit removes it. Windows embedded DLLs and explicit unmaterialized executable-path overrides retain a single eager load. This is an explicit portability limitation, not a Windows speed claim.

The original import profile is retained at `.artifacts/startup-profile-2026-09-16/opentui-import.md`. Installation and patch regeneration are documented in [opentui-fork.md](../installation/opentui-fork.md).

## Performance evidence

The empty-buffer comparison copies identical Xi source into an ignored baseline directory and resolves only OpenTUI to the pristine 0.5.11 package. Both commands run from the same working directory with isolated HOME/XDG roots and the same 120×40 PTY. Source hashes are checked before/after; order is randomized per pair. There are 30 fresh-process/filesystem-warm samples per variant plus excluded warmups. Boundary: external spawn to the existing first-frame marker, not physical visible pixels.

| Empty source launch | p50 | p95 | p99 / max |
|---|---:|---:|---:|
| Original OpenTUI | 200.74 ms | 210.29 ms | 212.04 ms |
| Fork | 130.39 ms | 141.39 ms | 151.27 ms |

Median main-process RSS sampled at that boundary fell from 91.84 to 84.78 MiB. CPU sampled from `/proc/<pid>/stat` was p50/p95 210/220 ms before and 140/150 ms after; these counters have 10 ms scheduler-tick resolution and are sampled just after the wall boundary. They are diagnostic, not precise CPU gate evidence. Total allocations, worker memory and retained/native breakdowns remain unmeasured.

Reproduction: `python3 .artifacts/startup-profile-2026-09-16/source-pair.py`; raw samples and source manifest: `source-pair.json` in that directory. The general comparative runner is [startup-diagnostic.py](../../bench/performance/startup-diagnostic.py).

## Reproduced failures and corrections

- The first lazy-binding implementation failed the actual compiled CLI with `Failed to get next buffer`: repeated Bun executable-path loads had separate native renderer state. The materialization fix and a compiled renderer regression prove shared state and cleanup; the isolated Xi distribution suite then passed.
- Upstream tests initially exposed readonly resolved symbol properties. The helper now preserves writable symbol properties, including replacement/restoration used by existing library consumers and tests. All borrowed-pointer callsite regressions pass after the fix.
- Original source-tree upstream failures: 12 Kitty file-transport cases and one missing `src/parser.worker.js` asset manifest case. An unchanged upstream checkout reproduces the exact 13 failing fixture names. They remain failures, not waived tests.
- Initial named-file diagnostic runs (`baseline-v2`, `final`, `trace-final`) used the oracle helper's greedy OSC pattern, which could swallow the first frame through a later cursor-color OSC. Those named-file timings are **invalid and superseded**. The diagnostic now recognizes BEL/ST termination separately, with a minimized regression in `bench/performance/test_startup_diagnostic.py`; `trace-final/xi-compiled-1.ansi` retains the actual reproduction. Empty-buffer marker measurements never use this matcher and remain valid. The shared oracle helper still needs its own independently reviewed correction; no oracle goldens were changed here.
- The initial edit/save harness used fixed delays around Escape and could send `:wq` while the editor still showed Insert. It now waits for observed mode transitions after injecting the first edit at the measured startup boundary. Final saved bytes must equal the exact expected edit. This correction does not certify arbitrary burst handling.

## Limitations and next action

No dedicated reference host, physical display capture, complete terminal-cell/cursor comparison, large-file loading matrix or 10,000-event loaded input matrix was collected. Helix and Neovim are clean configurations in a responsive synthetic terminal, not the user's live terminal. The corrected named-file boundary detects fixture content, cursor visibility commands and synchronized-update closure; it is output-byte evidence, not key-to-photon evidence. First-input mode timing is diagnostic and cannot replace the full spec 15 correctness matrix.

Bindings still cost time on first use; the direct cached path avoids repeated lookup overhead. Broad feature/lifecycle tests preserve behavior, but unmeasured cold feature tails remain unproven. Unix extraction requires writable temporary storage; SIGKILL cannot run cleanup. Windows compiled startup remains eager, and non-Linux platform qualification is outstanding.

T122 implementation and evidence acceptance is complete. T064/T115 still require their own qualification without changing their previous prerequisites. T106/T116 and all original release budgets remain unproven where they were unproven before; no thresholds, features, tests or expected snapshots were weakened.
