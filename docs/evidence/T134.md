## Observable result

`spikes/ui-react/components.tsx` implements an 80-line declarative shell. Problems
and Messages reuse Panel and Row components and one theme context. Standard
`useSyncExternalStore` subscriptions read the real DiagnosticStore and
StatusMessageController. Messages can update without rerendering the sibling
Problems subscription. Only visible diagnostic rows become React nodes.

The shell accepts an editor child slot; it creates no writable text buffer and
implements no Vim semantics. The demonstration has theme switching, bounded list
scrolling, pointer selection, controller messages and responsive narrow layout.
This establishes component reuse and state ownership, not production panel parity.

The spike is separately installed and typechecked. Root package.json, bun.lock and
tsconfig.json were not modified by this task. React is not loaded by production Xi.

## Performance and visual evidence

| Source import | Median import ms | Median process RSS MB (decimal) |
|---|---:|---:|
| Core renderer entry | 34.29 | 64.62 |
| Full Core | 44.02 | 67.63 |
| React adapter | 54.26 | 72.48 |

This is an import-only diagnostic with a filesystem-warm shared host, **not editor
startup, compiled startup or allocated-byte accounting**. React's broad Core catalogue
adds work relative to Xi's intentionally narrow entry, so production adoption requires
a real compiled startup comparison. No numeric release budget is certified.

The earlier scheduling investigation's public-Core / React / React-flushSync probe
and six raw result sets are retained in `.artifacts/react-investigation/`. All reached
the final count and stopped painting at idle; its fixed-order 120-event memory-backed
tests are not comparative production latency evidence. Both approaches use Core's
same terminal scheduler. React does not replace Xi's command serialization.

Real xterm images were opened and inspected. Wide light layout has aligned shared
panel borders, headers and diagnostic rows. Narrow dark layout stacks both panels,
keeps the footer visible, and clips long row text within panel bounds. This is a
demonstration design, not an approved replacement for production styling.

## Decision and integration gaps

The evaluation supports declarative components for shell/panel composition. They
can replace repeated creation, visibility setters, resize/bounds setters for ordinary
layout, theme fan-out, and manual subscription cleanup. Merely wrapping existing
classes would not remove their painting and lifecycle complexity.

Keep the custom editor viewport and semantic input router. Production adaptation
still needs generation-aware pointer handling, focus/cancel rules, keyboard navigation,
drag/wheel scrollbars, cursor-relative popups, and error/lazy-load boundaries. The
prototype intentionally does not claim those features. Its new dependencies remain
isolated while T133 scheduling and all existing performance gates are unproven.

Next production slice: one real panel with shared Panel/Row presentation and a
shell boundary, preserving existing controllers and the native custom viewport;
compare exact behavior, compiled startup, loaded input/output tails and allocation
before adopting it. No ticket completion here unlocks or certifies T111/T115/G6.
